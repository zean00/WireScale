a pre-registered laboratory for decision structure

how should a
machine decide?

Step by step down a tree like twenty questions — or all at once, like reading the whole menu? WireScale measures where each strategy wins, across five uses: hierarchical decisions, routing users to specialist agents, filtering a toolbox down to the useful tools, finding the right page in a corpus, and traversing a map of facts.

96-leaf trees, 6 levels deep 64 specialist agents routed 121 real tools filtered to ~65 58 frozen questions over a 180-page corpus 902-triple knowledge graph 21/37 headline predictions passed as registered — the failures map the dead ends
the experiments
the premise

One frozen brain, many tiny ways to decide.

WireScale never trains the big model. A language model turns sentences into points in space (embeddings) and stays completely frozen — the way a thermometer doesn't change when you read it. All the experimenting happens in the tiny readout attached on top: a few thousand parameters that look at the point and make a choice. That makes every experiment cheap, fast, and ruthlessly comparable.

the substrate

Embed + measure

Every sentence becomes a vector from a frozen model — the Qwen3.5-4B encoder (2,560-dim) for decisions, later joined by a dedicated 0.6B embedding model for retrieval. A "readout" is just distances and ranks: which reference point is closest?

the discipline

Register before data

Predictions, arms, and pass/fail bars are committed to the repo before any experiment runs. Verdicts are computed mechanically by a script, not argued afterwards.

the honesty

Failures are results

In the first experiment, all four registered predictions failed or flatlined — and that was published as the headline. A botched first run was deleted unexamined and disclosed.

🌿

Why trees at all? A tree decides like twenty questions: Is this about the house? → About lights? → About brightness? Each step is easy to inspect and trust. The alternative reads the whole menu in one glance. Trees cost you if an early step is wrong — every later step then inherits the mistake. Everything WireScale measures is a variation on that one trade-off: easy steps that compound vs one glance that doesn't.

use case 1 — hierarchical decisions

The decision tree: does the parent's answer help the child?

Build a tree of commands — smart home → lights → brightness — up to 6 levels and 96 final answers, from synthetic sentences whose true answer is known by construction. Then ask the registered question: if each level's little readout is told what its parent decided ("conditioning"), does the tree stop getting worse as it grows?

in plain terms

Twenty questions, with a cheat sheet

Imagine the twenty-questions player writes down each answer and hands it to the next questioner — that's parent conditioning. Intuition says it must help. The lab found it barely matters: what matters is whether the words themselves say which final answer is meant.

The lab controls that with a dial called markedness: at m=1 every sentence names its leaf; at m=0 two sibling leaves get identical sentences — no method on earth can split them.

the contenders

Five ways to walk down

A — flat: one glance at all leaf labels. B — walk: greedy, one level at a time. C — walk + parent hint: the conditioning hypothesis. C′ — a fancier hint (FiLM). E — beam-2: like the walk, but keeps two candidates alive at each level.

All share the same frozen encoder; readouts are linear trunks scored by centroid cosine; accuracies are template- and vocabulary-transfer (eval sentences use held-out words).

When they aren't, every architecture sits at a coin flip. use case 2 — agent routing

The concierge: which specialist gets the request?

Modern agent frameworks keep a bench of specialists — a git agent, a calendar agent, a shopping agent — and something must route each user message to one of them. WireScale built 8 departments × 8 specialists = 64 sub-agents and asked: is the two-step concierge (department → specialist) better than one flat glance at all 64?

🛎️

In plain terms: a hotel concierge first picks the department ("engineering"), then the specialist inside it. If the guest names the specialist's specialty, one flat glance at the staff directory routes 93% of guests correctly (random chance: 1.6%). But if the guest only says "something with the projector, please" — never naming a specialist — no concierge on earth can do better than chance at the specialist level, even one who secretly knows the right department. That's not a routing failure; it's the sentence carrying no routing information.

registered honesty · S-series amendment 1

The first run was thrown away — unexamined archived, published

Pass 1 contained a scoring bug (the walk arms compared a number to a string — always false, so they recorded exactly 0.0, impossible as a measurement) and a substrate flaw: departments were built from generic vocabulary only, so they scored .39 on sentences that visibly named their department. Both were fixed and disclosed before the real run; the invalid file ships in the repo as the record. A follow-up probe found the real culprit — shared template filler drowning the signal — and fixed it with a two-pair template, with the composition probes that didn't help also recorded.

🧭

Verdict for routing: nameability is the whole game. A router cannot pick a specialist the utterance never names — so real sub-agent systems need requests that carry identifying content, or a graceful fallback to department-level service. And at this scale, coarse-first routing is a liability, not an engine: it caps you at the coarse level's error rate. The lab-parked conclusion: flat when embeddings are strong; walk only when the coarse level is near-perfect; beam-2 either way.

use case 3 — tool selection (filtering)

The workbench: 121 tools on the wall, only the useful ones on the bench.

This is where the lab met production. A voice assistant has 121 real tools (GitHub, filesystem, git, smart home…). Showing all of them to a small model every turn costs tokens and accuracy. The measured alternative: embed the request, keep only the tools whose reference points are close — then let the model choose from the short menu.

in plain terms

The librarian and the sticky note

A librarian grabs the two most likely shelves (~65 of 121 tools) — reliable, 88% of the time the right tool is on the bench. A sticky note ("this looks like git work") turned out to be the single biggest picking boost ever measured in the program… and it broke refusals: shown the note, the model grabs a tool even for "what's 15% of 240?"

A separate quick question — "does this even need a tool?" — is the best refusal-detector ever measured, and worthless as a gatekeeper: used as one, it turns away a quarter of real requests.

the composition that worked

Let the guard control only the note

Chat-detected → normal workbench, no note (never turned away). Tool-detected → workbench plus the note. Each helper's weakness is absorbed by the other's strength. Then the recall fix from WireScale's own walk playbook (keep two first-level candidates — beam-2) widened the bench coverage from 88% to 96%.

Every step was pre-registered; three popular ideas were rejected on measurement first (search-as-a-tool, no-tool-as-a-menu-item, the hard two-step gate).

the ledger of rejected ideas · all pre-registered

What didn't work measured, not vibes

Search-as-a-tool (let the model query a tool directory): 49% — its short queries surfaced the target only 51% vs 88% for embedding the utterance itself. Sliding windows over the tool list: positional, so they lose the right tool half the time. no_tool as a menu item: rescued the tricky refusal cases but siphoned 54 real requests into "no tool". The hard two-step gate: best refusals ever (23/24), turned away 62 genuine requests. The bare hint: record accuracy, wrecked refusals (15/24). Every one of these failures is load-bearing — the final design is what's left after they're subtracted.

🔧

Verdict for tool filtering: the production design is now recall-first filtering + a refusal-guarded hint — 73.4% vs 67.3% for the shipped gate, registered as the wiring target with costs priced (one extra local model call per request, ~a tenth of a second). And a transfer lesson travelled the other way too: this lab's beam-2 deploy in the assistant's router only worked after discovering that paths of different depth must be scored with mean, never sum — a 13-point crash lived entirely in that choice.

use case 4 — retrieval (the RAG season)

The librarian and the fact-checker: find the page, then verify it.

Everything above decides among fixed labels. The second season asks the everyday question behind every chatbot that "reads the documentation": who finds the right page — and should anyone check it before answering? The corpus is the lab's own docs: 180 pinned chunks and 58 frozen, hand-audited questions (half asked in the page's own words, half asked as a human need would be). Nine scored experiment groups later, the answer is a machine.

📚

In plain terms: two workers. A fast librarian (a small dedicated embedding model) glances at every page and ranks them by "probably relevant" — nearly free, and it never actually reads. A careful fact-checker (the frozen 4B, asked a strict yes/no per page) is rarely fooled but must read to judge. The measured recipe: let the librarian set the order, let the fact-checker read pages one at a time in that order, stop at the first confident yes, and if nothing convinces it, fall back to the librarian's top pick. Every ingredient was registered and scored separately — then the assembled machine was registered and scored too, and all four of its predictions passed, the first clean sweep in the lab.

what worked

Sort, verify, stop, fall back

Scanning pages in the librarian's order and stopping at the first confident yes reaches .690 prefix-recall — above the exhaustive reader's .517 — while judging a mean 11.5 of 180 chunks at 15.8% of the tokens. One temperature (T=0.66) makes the checker's confidence honest (held-out ECE .105 → .081), and the assembled machine turns that into answers: .431 vs .345 for plain vector RAG, at 18.6% of the read-everything cost.

what didn't — the measured dead ends

Every "help" hurt

The frozen 4B doing embeddings as a side job ranked at random, and no rescue dial fixed it (pooling, prefixes, truncation, a trained pair head at 8× data). Rewriting the user's question made retrieval worse (−6.9 indirect), and so did the embedder's own official instruct prefix (−3.5). The raw question, verbatim, beat every attempt to improve it.

🔍

Verdict for retrieval: pure vector search is a librarian, not a reader — and the reader is worth it. Rank with the dedicated embedder, verify with the judge in that order, stop when the calibrated confidence crosses the bar, fall back to rank-1 when nothing does. And it survived the fair fight: when RAG got its real production form — top-k excerpts in one prompt — stuffing in more pages raised context hit (.45→.81) but answer accuracy flatlined (.33–.40), because synthesis collapses as context grows (.77→.43). One judge-verified page beats eight candidates. The ending is a merger, not a winner: the machine now reads RAG's own shortlist — scan the top-8, stop at the first verified page, answer from that page alone — keeping .414 of the full machine's .431 at 40.6% of its cost. Honest losses, disclosed in the ledger: even holding the right page the answer sometimes comes out wrong (−3.4 pts from synthesis), questions asked in roundabout ways stay hard (.207), the pool's gold is captured only .466 of the time (the verifier is the binding constraint), and plain top-2 RAG keeps the per-token crown (92% of the machine's accuracy at 21% of its cost).

use case 5 — knowledge graphs

The map of facts: walk it, hedge it, or read it flat?

A knowledge graph answers questions by traversal: start at an entity, follow relations, arrive at the answer. The lab extracted a 902-triple graph from the same pinned corpus, wrote 60 path-grounded questions with known gold paths (audited before freezing), and registered the decision-layer question: is a guided walk smarter than just reading?

amendment 2 — the operator's design, registered

Route lookahead: right instinct, wrong commitment

The proposal: pick a starting node, enumerate all routes up to 3 hops, have the model choose the most promising whole route, re-anchor at its destination, repeat. Both verdicts FAIL — LOOK-1 landed below the plain greedy walk, LOOK-2 collapsed to 2/60. The diagnostic explains it: the gold node sat on the chosen route 32% of the time, and the walker walked past it nearly every time — a 3-hop route overshoots a 2-hop answer.

amendment 3 — score the path, not just the destination

The vindication hiding in the failure

Re-scored fairly — credit for reaching the right neighborhood — the story flips: beam-2's visited paths contain the gold .300, beating retrieve-then-read's .233 (registered KM1 PASS), and the operator's LOOK-2 posts .333, the best graph number in the lab. The design navigates well and then overshoots the final step. On graphs: hedge, never commit — and score what the walker actually visits.

🗺️

Verdict for graphs: the map itself is the ceiling — machine-extracted triples cap entry-point visibility at .53, so no traversal policy can answer what the map doesn't reach. Given that substrate, hedged walkers are the best navigators ever measured here, flat reading still wins when it fits, and committing to one route — however cleverly chosen — loses twice over.

what transfers

Six laws, paid for in full.

law 01

Information bounds; structure spends

When the text names its answer, every architecture works (96 leaves at 95.9%). When it doesn't, nothing does — coin flips at the leaf (m=0) and chance at the specialist (1/8), oracle included. Diagnose the sentence before redesigning the tree.

law 02

Early steps tax everything after

A walk inherits its first mistake: 91.8% at the root caps a 6-level walk at .825 no matter how perfect the deeper levels (.9997, 1.0). Flat overtakes the walk once the class count grows — at 96 classes, .899 vs .825 — and on graphs, flat wins whenever the map fits (K3).

law 03

Hedge; never commit

Keep two candidates alive at the coarse level: +3.4 pts at 96 leaves, +7.7 pts on agent routing, +13.3 on graph traversal — four replications, the largest margins in the lab. One caveat: score paths by mean, never sum (a 13-point crash hid in that choice).

law 04

Register, then obey the verdict

The first experiment went 0 for 4 — so conditioning was stopped by rule. Since then: 18 of 34 headline predictions passed as registered, and every failure is kept as a mapped dead end — including the operator's own pre-registered bet that plain top-k RAG would beat the machine (it didn't). Runs botched or invalidated are deleted unexamined and disclosed. The ledger is the product.

law 05

Sort, verify, stop — then fall back

A ranking is not an answer. Let the cheap model order the pages, let the careful model check them one at a time until confident, and keep a safe fallback for when it never is: .431 vs .345 for plain vector RAG at 18.6% of the read-everything cost — still .414 vs .397 confined to RAG's own top-8 shortlist at 40.6% of the cost (the pool costs one question, where gold hides beyond rank 8). The verifier beats the guesser, the brute, and the pile.

law 06

Helping the input hurts

Three times measured: the embedder's official instruct prefix (−3.5 pts), LLM query rewriting (−6.9 indirect, −3.5 direct), and now context stuffing — top-k RAG's synthesis given gold-in-context collapses .77 → .43 from k=1 to k=8 while context hit climbs .45 → .81, so accuracy flatlines. The raw question wins and one verified page beats eight candidates. If confidence is the problem, calibrate the judge (T=0.66; ECE .105→.081) — don't edit the question or pad the context.

Every number on this page is a committed artifact.

Hypotheses, arms, bars, and amendments live in protocol.md; raw scored runs in results/*.json. Verdicts are computed mechanically (adjudicate.py), not argued. The frozen encoder is never fine-tuned; embeddings are served on a dedicated slot so the production system is never touched. Local commits only — published as-is, in the spirit of the ledger: register first, measure, admit when wrong.
